# Device->host reads through the BAR4 window

- **Date**: 2026-10-16
- **Task**: Solar decode latency
- **Host / device**: etri-ESC8000-E11, 2x RNGD (driver 2026.4, furiosa-opt 0.9.0), Xeon 4410Y x2
- **Commit**: bb532fd

## Question
Can small downloads (h2 8 KB, chip-B output 8 KB) beat DMA (~50 µs) by reading the BAR window?

## Setup
Microbench: UC 64-byte loads cost ~0.7 µs per line per core but overlap across cores (8 KB: 1 thread 88 µs, 8 threads 11 µs).
Engine: `MMIO_RLIMIT` + read hook. v1 ran an OpenMP team from the chip thread; v2 lets the waiting main thread serve the read with its idle OpenMP team (`MMIO_RT=17`).

## Command
```bash
MMIO_RT=17 MMIO_RLIMIT=16384 MMIO_VEC=2 MMIO_LIMIT=32768 ... REPEAT=5 ./target/release/solar_engine data_p2 32   # interleaved with baseline, load < 3
```

## Results
| config | decode ms/tok (2 runs) | L.dl µs |
|---|---:|---:|
| baseline DMA | 30.1 / 30.2 | 51-60 |
| v1 (OMP team on chip thread) | 220-320 | - |
| v2 (main thread serves) | 30.3 / 30.5 | 44-47 |

## Conclusion
Exact but neutral end to end; v1 oversubscribes cores. Kept off by default.
